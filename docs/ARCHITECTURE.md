# Архитектура системы

**Версия:** 0.1 (предложение к утверждению)
**Дата:** 2026-06-02

Документ описывает архитектурные принципы, по которым строится POS-система. Без понимания этих принципов добавление любого нового модуля (склад, рейтинги, директорская версия) превратится в латание дыр.

---

## 1. Базовые принципы

### 1.1. Сервер — единственный источник правды

Никаких локальных SQLite на устройствах для бизнес-данных. Любое изменение заказа, столика, меню, оплаты происходит **только через API**. Клиент — это «тонкий» вид над состоянием сервера.

> *Почему:* в зале 5 планшетов, на каждом своя копия БД = пять разных «правд». Никакая отчётность не сойдётся.

### 1.2. Event log — основа отчётности и аудита

Каждое изменение состояния (особенно денежного) записывается в **неизменяемый журнал** `audit_log`. Отчёты строятся из журнала, а не из текущего состояния. Это значит:

- Можно построить отчёт за любой день, не «портя» БД.
- Можно восстановить, кто и когда добавил/удалил позицию (для разборок с гостями и сотрудниками).
- Финансовые отчёты бьются «в копейку», потому что считаются на основе истории, а не текущего среза.

### 1.3. Optimistic UI + push через WebSocket

Клиент сразу показывает результат локально (не ждёт сервер), параллельно шлёт команду, при ошибке откатывает. Все остальные клиенты получают изменения **пушем** через WS. Polling не используется.

### 1.4. Offline-first для планшетов в зале

Если Wi-Fi моргнул:
- Меню, столики, активные заказы есть в локальном кэше.
- Действия (добавить позицию, отправить на кухню, принять оплату) копятся в очереди.
- При восстановлении — синхронизация с разрешением конфликтов «победил последний».

Для QR-клиента offline не делаем — он в браузере, при потере связи просто перезагружает страницу.

### 1.5. Модули — самодостаточные

Каждый функциональный блок (заказы, склад, рейтинги, директор) — отдельный модуль с:
- своими миграциями БД,
- своими роутами в `routes/api/<module>/`,
- своими репозиториями,
- своими WS-событиями.

Модули можно включать/выключать на уровне ресторана (через настройки), и они не должны ломать друг друга.

### 1.6. Роли + права (RBAC)

Сейчас четыре роли (waiter/cashier/cook/admin). Будут добавляться (director, warehouseManager, host). Чтобы это не разрослось в кашу:
- роль = набор **permission'ов** (`orders.create`, `reports.view_full`, `menu.edit`, `warehouse.write_off`),
- проверка прав на сервере для каждого endpoint,
- админ может создавать свои роли (например, «старший официант» с дополнительными правами).

                       │
┌──────────────────────▼─────────────────────────────────────┐
│              ДОМЕННЫЙ СЛОЙ (server/lib/src/domain/)        │
│  Бизнес-правила, валидация, event-эмиссия                  │
│  - OrdersService                                            │
│  - PaymentsService                                          │
│  - WarehouseService                                         │

└──────┬───────────────┬─────────────────────┬───────────────┘
       │               │                     │
┌──────▼──────┐ ┌──────▼──────┐ ┌────────────▼────────────┐
│ Repository  │ │  EventBus   │ │    Audit Log Writer     │

**Сейчас репозитории и роуты переплетены** (в роуте напрямую вызываются методы репо). Это нормально для прототипа, но со ввозом сложных модулей (склад, отчёты) пора вынести **сервисный слой**: роут только парсит запрос → передаёт команду в сервис → сервис проверяет права, валидирует, меняет несколько таблиц атомарно, пишет в audit, эмитит событие.

### 3.1. Новые / уточнённые сущности

| Сущность | Зачем | Когда добавляем |

| **Ingredient** | Сырьё на складе | Спринт 8 (склад) |

| **Role** (вместо enum) | Группировка прав | Спринт 7 |

### 3.2. Уточнение существующих

**Order** — добавить:
- `source`: `waiter` | `qrPreorder` | `reservation` | `phone` | `delivery` (расширяемый)
- `sessionId`: один стол может закрыть несколько заказов за сессию (пришла группа, заказали, закрыли счёт, пришли новые — это разные `Order`, но один `Session`)
- `shiftId`: к какой смене относится
- `originDeviceId`: с какого устройства был создан (для отчёта «продажи по терминалам»)

**OrderItem** — добавить:
- `addedByUserId`: кто добавил (для аудита и рейтингов «официант продал больше всех десертов»)
- `cancelledByUserId`, `cancellationReasonId`: при отмене
- `compTicketId`: если позиция за счёт заведения

**Payment** — добавить:
- `tipAmount`: чаевые отдельно от основной суммы
- `commissionAmount`: эквайринговый сбор (для отчёта о реальной выручке)
- `cardLast4` (опц.): для сверки с банком

## 4. Синхронизация — как именно

### 4.1. Базовый поток (online)

```
Officiant tablet            Server                  Other clients
       │                       │                          │
       │── POST /orders ────▶  │                          │
       │   (optimistic UI:     │                          │
       │    показал заказ      │                          │
       │    сразу)             │                          │
       │                       │── INSERT INTO orders ──▶ DB
       │                       │── INSERT INTO audit ───▶ DB
       │                       │                          │
       │ ◀── 201 + Order ──────│                          │
       │   (фиксируем id)      │                          │
       │                       │── WS: order.updated ───▶ │
       │                       │── WS: table.status ────▶ │
       │                       │                          │
       │                       │                          ▼
       │                                          обновили UI
```

### 4.2. Конфликты

Сценарий: официант А и официант Б одновременно редактируют один заказ.

**Решение — optimistic locking через `version`:**
1. У каждого `Order` есть поле `version` (увеличивается с каждым изменением).
2. Клиент при апдейте передаёт `If-Match: <version>` (или в теле запроса).
3. Если на сервере уже другая версия → сервер возвращает `409 Conflict` + актуальный заказ.
4. Клиент показывает диалог «заказ изменён другим официантом, посмотри актуальную версию».

### 4.3. Offline режим для планшетов

**Что кэшируется локально (sqflite на устройстве):**
- Меню (категории, блюда, цены, модификаторы)
- Список столиков и их статусы
- Активные заказы текущей смены
- Свой пользователь и сессионный токен

**Outbox-очередь команд:**
- Когда нет сети, команды (`addItem`, `sendToKitchen`, `pay`) пишутся в локальную таблицу `outbox`.
- При восстановлении сети — отправляются по порядку.
- Если конфликт (`409`) — приостанавливаем синхронизацию, спрашиваем пользователя.

**Что НЕ делаем offline:**
- Логин (первичный — нужна сеть).
- Платежи безналом (банковский эквайринг и так требует сеть).
- Печать чека кухне — её делает сервер, а не клиент.

### 4.4. WebSocket: восстановление состояния

При (ре)коннекте сервер шлёт клиенту **снимок состояния** (full state push), потом дальше — только дельты:

```
WS: connect
WS: << system.snapshot { tables: [...], activeOrders: [...] }
... через 30 сек ...
WS: << order.updated { ... }
```

Это решает проблему «пока сеть мигнула, я пропустил 3 события».

## 5. Журнал событий и аудит

### 5.1. Таблица `audit_log`

```sql
CREATE TABLE audit_log (
  id TEXT PRIMARY KEY,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  user_id TEXT,                    -- кто (может быть null для системных)
  device_id TEXT,                  -- с какого устройства
  action TEXT NOT NULL,            -- 'order.create', 'item.cancel', 'payment.add', ...
  entity_type TEXT NOT NULL,       -- 'order', 'order_item', 'payment', 'table', ...
  entity_id TEXT NOT NULL,
  before_json TEXT,                -- состояние ДО (или null для INSERT)
  after_json TEXT,                 -- состояние ПОСЛЕ (или null для DELETE)
  metadata_json TEXT               -- доп. контекст: причина, IP, версия клиента
);
CREATE INDEX idx_audit_entity ON audit_log(entity_type, entity_id);
CREATE INDEX idx_audit_user_time ON audit_log(user_id, created_at);
```

### 5.2. Что пишем в audit

Минимум: **всё, что меняет деньги или влияет на сервис гостя**.

- Создание/изменение/закрытие заказа
- Добавление/отмена/изменение qty позиции
- Изменение статуса позиции на кухне
- Все платежи и компенсации
- Смена цен в меню
- Открытие/закрытие смены
- Манипуляции пользователями (создание, смена роли, бан)

### 5.3. Что **не** пишем

- Чтение (запросы GET) — иначе журнал распухнет.
- Технические события (соединение/отключение WS).

### 5.4. Реализация

Сервисный слой пишет в audit перед коммитом транзакции БД. Помощник:

```dart
await audit.record(
  action: 'order.send_to_kitchen',
  user: currentUser,
  entityType: 'order',
  entityId: orderId,
  before: oldOrder.toJson(),
  after: newOrder.toJson(),
);
```

## 6. Отчётность (бухгалтерия)

### 6.1. Уровни отчётов

| Уровень | Кто смотрит | Период | Содержание |
|---|---|---|---|
| **X-отчёт** | Кассир / админ | Текущая смена | Промежуточные продажи (без закрытия) |
| **Z-отчёт** | Кассир / админ | За смену | Закрытие смены: выручка, инкассация, выручка по способам, по официантам, по категориям |
| **Дневной** | Админ / директор | За день | Все смены за сутки, средний чек, заполняемость столов |
| **Период** | Директор | Произвольный | Сравнение периодов, тренды, ABC-анализ блюд |
| **По официанту** | Директор | Произвольный | Выручка, средний чек, продажи доп. позиций, рейтинги от гостей |
| **По блюду** | Шеф / директор | Произвольный | Сколько продано, в какие часы, какая маржа |
| **По источнику** | Директор | Произвольный | **Сколько от QR, сколько от планшета**, конверсия предзаказов |

### 6.2. Архитектура отчётов

**Принцип:** отчёт = SQL-запрос к `orders` + `order_items` + `payments` + `audit_log`, агрегированный по нужным измерениям.

**Не делаем сложный OLAP сейчас.** SQLite вполне тянет 100K+ строк в месяц. Если когда-то упрёмся — мигрируем на Postgres.

Все отчёты — на стороне **сервера**, клиент только запрашивает готовый JSON:

```
GET /api/reports/z-report?shiftId=...
GET /api/reports/daily?date=2026-06-02
GET /api/reports/by-waiter?from=2026-06-01&to=2026-06-30
GET /api/reports/by-source?from=...&to=...&group_by=day
GET /api/reports/abc-dishes?period=30
```

### 6.3. Пример: «выручка по источникам»

Один SQL даёт сразу детальную картину:

```sql
SELECT
  o.source,                        -- waiter / qrPreorder
  COUNT(DISTINCT o.id) AS order_count,
  SUM(item_total)      AS gross_revenue,
  AVG(item_total)      AS avg_check,
  SUM(CASE WHEN p.method = 'cash' THEN p.amount ELSE 0 END) AS cash,
  SUM(CASE WHEN p.method = 'card' THEN p.amount ELSE 0 END) AS card
FROM orders o
LEFT JOIN (
  SELECT order_id, SUM(qty * price_at_moment) AS item_total
  FROM order_items WHERE status != 'cancelled'
  GROUP BY order_id
) oi ON oi.order_id = o.id
LEFT JOIN payments p ON p.order_id = o.id
WHERE o.closed_at BETWEEN ? AND ?
GROUP BY o.source
```

Результат:

| source | orders | gross | avg_check | cash | card |
|---|---:|---:|---:|---:|---:|
| qrPreorder | 142 | 358 500 | 2 525 | 95 000 | 263 500 |
| waiter | 89 | 215 800 | 2 424 | 102 000 | 113 800 |

В UI директора это превращается в красивую таблицу с диаграммой и фильтрами.

### 6.4. Экспорт

- **PDF** (Z-отчёт для подшивки) — pdf-генерация на сервере (например, через `pdf` пакет).
- **Excel/CSV** для бухгалтера — `csv` пакет, выгрузка одним кликом.
- **Печать на чековом принтере** — Z-отчёт на 80-мм ленте.

## 7. Модуль «Рейтинги и отзывы»

### 7.1. Сценарий «гость оставляет отзыв через QR»

После того как кассир принял оплату, статус заказа переходит в `paid`. WebSocket пушит событие на устройство клиента (если он ещё в браузере с QR-страницей):

```
WS << order.paid
    → клиент показывает экран "Спасибо! Оцените, пожалуйста"
```

Экран:
- 4 шкалы по 5 звёзд: **еда / сервис / скорость / в целом**.
- Указать имя официанта (или мы знаем его автоматически).
- Текстовый комментарий (опц.).
- Чаевые официанту (опц., если включён эквайринг).

### 7.2. Данные

```sql
CREATE TABLE reviews (
  id TEXT PRIMARY KEY,
  order_id TEXT REFERENCES orders(id),
  waiter_id TEXT REFERENCES users(id),
  source TEXT NOT NULL,            -- 'qr', 'manual_email', 'phone'
  rating_food INTEGER,             -- 1..5
  rating_service INTEGER,
  rating_speed INTEGER,
  rating_overall INTEGER,
  comment TEXT,
  guest_contact TEXT,              -- если оставили (телефон/email)
  manager_response TEXT,           -- ответ менеджера
  manager_responded_at TEXT,
  is_published INTEGER DEFAULT 0,  -- модерация перед публикацией
  created_at TEXT NOT NULL
);
```

### 7.3. Что показываем директору

- Средний рейтинг ресторана за период (по 4 шкалам).
- Топ-10 / Анти-топ официантов по рейтингу.
- Все комментарии с фильтром «без ответа менеджера».
- Корреляция рейтинга с выручкой/посещаемостью.
- Алерт: если у официанта рейтинг ниже 3.5 за неделю — уведомление директору.

### 7.4. Альтернативные источники отзывов (будущее)

- SMS/email клиенту через 2 часа после оплаты (если оставил контакт).
- Telegram-бот с напоминанием.
- Виджет на сайте ресторана.

Структура `reviews.source` позволит всё это сложить в одну таблицу.

## 8. Будущие модули (roadmap)

### 8.1. Версия для директора (мобильная)

Отдельный экран в POS-приложении (или **отдельный мобильный app** для удалённого доступа). Что показывает:

- **Дашборд** прямо сейчас:
  - выручка с начала смены,
  - количество гостей в зале (сумма `guestsCount` открытых заказов),
  - top-3 официанта дня,
  - заполняемость столиков (диаграмма зала),
  - очередь на кухне (среднее время приготовления).
- **Отчёты** (см. раздел 6).
- **Рейтинги** (см. раздел 7).
- **Алерты**: длинная очередь на кухне, низкий рейтинг, упавший принтер, низкий остаток ингредиента.
- **Кнопка «отдать комп»** — даже без присутствия (написать менеджеру → менеджер на месте оформляет).

Технически — это новый «режим» в Flutter app с другой нижней навигацией и фильтром по правам.

### 8.2. Модуль «Склад»

Самый сложный из будущих модулей. Базовая модель:

```
Ingredient (мука, помидор, мясо)
  ├ unit (кг, шт, литр)
  ├ stockQty
  ├ minStockQty (порог для алерта)
  └ supplier

Recipe
  ├ dishId
  └ items: [{ingredientId, qty}]

StockMovement
  ├ type: income | expense_auto | writeoff | inventory
  ├ ingredientId
  ├ qty
  ├ reason
  └ documentId  -- связь с накладной / актом списания
```

**Автоматическое списание:** когда статус OrderItem меняется на `served` или `ready`, движок берёт рецепт и **автоматически** делает `StockMovement type=expense_auto`. Если ингредиента не хватает — алерт менеджеру.

**Инвентаризация:** периодический пересчёт; расхождения логируются в audit.

**Себестоимость:** для каждого блюда считается из текущих цен ингредиентов → отчёт по марже.

## 11. Открытые вопросы и принятые решения

### 11.1. Зафиксированные решения

| # | Решение |
|---|---|
| **A4** | **Рейтинги показываем сразу в QR-окне** после оплаты. Сервер шлёт WS `order.paid` → QR-страница автоматически переключается на экран «оцените, пожалуйста». Это даёт максимальную конверсию (гость ещё за столом, ещё в браузере). Возможность собрать email/телефон для отложенного отзыва — оставляем на будущее. |
| **A5** | **Склад — полноценный, на уровне ингредиентов.** Сущности: `Ingredient` + `Recipe` (блюдо → состав) + `StockMovement` (приход / расход / списание / инвентаризация) + автосписание по рецепту при `OrderItem.status = served`. Дополнительно — себестоимость каждого блюда и отчёт по марже. Это полноценный спринт (~8 дней), но даёт реальный учёт, а не «галочку». |
| **A6** | **Директор — пока только локально** (с того же Wi-Fi заведения). Удалённый доступ через HTTPS-туннель + аутентификация по 2FA — оставляем на будущий этап (после стабилизации основной части). |
| **A7** | **Offline-режим планшета — полноценный**, с локальным кэшем (sqflite) и outbox-очередью. Делаем «как будто Wi-Fi плохой», потом если окажется что сеть нормальная — лишний труд оправдается надёжностью (один уронил Wi-Fi роутер → касса не встала). |
